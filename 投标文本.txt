【详细方案】
Understanding
The ticket asks for one aggregation endpoint over `sales_lead_stage_logs`: a cohort by registration window, a distinct "ever reached" count per stage, adjacent-stage and overall conversion with a null denominator rule, dwell mean and median in days rounded to one decimal, lost-reason and lost-stage distributions, and a source-channel split. I read both the task page and its JSON representation, including the four acceptance criteria, and I treat those four lines as the review contract. The requested delivery stack for this ticket is Node.js 22, Express, an in-memory data layer, Playwright on Microsoft Edge and a React 18 / Vite 6 demo, so the implementation follows that stack while keeping the same metric semantics as the described SQL view.

Plan
1. Build a first-reach view keyed by lead and stage so repeat visits collapse to one reach and backtracking cannot double count.
2. Add aggregation for stage reach, adjacent conversion with null when the denominator is zero, overall conversion, dwell mean and median, churn distributions and channel split.
3. Expose the endpoint with inclusive date bounds, optional site, owner and channel filters, and role-based scoping.
4. Encode three hand-calculated examples once as data, use them in both the README and the tests, and expose them through the same aggregation code over HTTP.
5. Ship the React demo, run the Node and Playwright suites, benchmark P95 on 100000 synthetic leads and over 500000 stage logs, and record the real output.

Data sources
Only deterministic synthetic / fictional records are generated, with a fixed seed, so every reviewer reproduces the same numbers. Stage logs carry stage, entered timestamp, left timestamp, dwell seconds and an optional lost outcome with a reason. The first-reach view stores the earliest entry per lead and stage; dwell samples come only from logs with a left timestamp. The hourly refresh ticker rebuilds the view in memory, and no real personal, company or client information appears in any deliverable.

Why me
This proposal is specific to the ticket rather than a general promise: the deliverable list names eight files, the three hand-calculated examples are written into both documentation and assertions, and each acceptance criterion has a named test and an evidence file. The design keeps the metric engine independent of the demo and the transport, so a reviewer can check the arithmetic directly in the engine, check the HTTP behaviour in the browser suite, and re-run the P95 benchmark without any external service.

Implementation
No special access, client account, credential, cloud resource or third-party SDK is required. Path: read the criterion list -> implement `buildReachView()` as the in-memory counterpart of `mv_sales_lead_stage_reach` -> add `computeFunnel()` for reach, conversion, dwell, churn and channel metrics -> wire `GET /api/sales/stats/funnel` in `server.js` with inclusive date bounds and role scoping -> encode the three examples in `HAND_CALC_EXAMPLES` and reuse them in tests, README and an HTTP endpoint -> build the React 18 / Vite 6 console -> run `npm run test:unit` and `npm run test:e2e` on the msedge channel -> write the captured output into `验证记录.md`.

3. The 3 hand-calculated examples in the metric definition match the API output (test case)
4. P95 < 800ms on the test database with 500,000 stage log entries (performance script output attached)
